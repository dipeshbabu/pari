# Benchmarks

Pari treats benchmark evidence as part of performance-sensitive engineering. The benchmark code is separated from runtime crates and produces versioned JSON so results can be archived, compared, or generated by another engine.

The named scale campaign in `benchmarks/campaigns/scale-v1.json` is the canonical way to produce publishable evidence. It runs the existing measurement engines, validates correctness and provenance before accepting their reports, and bundles exact commands, logs, checksums, environment details, workload semantics, and the full Git commit SHA.

## End-to-end synthetic workload

Run the default release workload:

```bash
cargo run --release -p pari-bench -- run --output pari-benchmark.json
```

The default workload uses 5,000 deterministic 100-feature sets, 100 queries with 90 retained source features, 128 MinHash values, seed 7, and a target threshold of 0.8.

The report records:

- signature computation throughput
- index build throughput and elapsed time
- scalar query throughput and p50/p95/p99 latency
- batch query throughput
- candidate count
- candidate rate and reduction against all possible query-item pairs
- candidate recall and precision against exact Jaccard ground truth
- scalar/batch candidate parity and per-phase elapsed time
- delete plus reinsert throughput
- direct index grouping throughput
- streamed union-find edge throughput
- process RSS before, after, and sampled peak on Linux
- RSS delta per item where available
- OS, architecture, logical CPU count, Rust compiler, Git SHA, workload configuration, and report schema

Normal CI does not fail on wall-clock thresholds. Timing is noisy across shared runners, so performance-sensitive PRs should attach or cite benchmark reports rather than turning runner variance into correctness failures.

## Smaller development run

```bash
cargo run --release -p pari-bench -- run \
  --items 1000 \
  --queries 25 \
  --output quick.json
```

## Persistent storage workload

Run the local persistence and lazy-query workload with the same configuration surface:

```bash
cargo run --release -p pari-bench -- storage \
  --items 5000 \
  --queries 100 \
  --output pari-storage-benchmark.json
```

The storage report uses the same versioned flat metric schema as the main benchmark and records:

- `storage.persistent.build_items_per_second`
- `storage.persistent.build_elapsed_ms`
- persistent build and reopen RSS metrics where supported
- `storage.persistent.file_bytes` and `storage.persistent.bytes_per_item`
- `storage.persistent.reopen_ms`
- `storage.persistent.committed_buckets`
- `storage.persistent.mutation_operations_per_second`
- `storage.persistent.sync_ms`
- `storage.persistent.mutation_parity`
- external-builder throughput, RSS, spill count, peak buffered records, bucket count, and output bytes
- `storage.lazy.reopen_ms`
- lazy reopen and query RSS metrics where supported
- `storage.lazy.file_bytes` and `storage.lazy.bytes_per_item`
- lazy scalar query throughput and p50/p95/p99 latency
- lazy batch query throughput
- `storage.candidate_parity`
- `storage.lazy.reopen_rss_to_file_ratio` when RSS sampling is available

The mutation/sync sub-workload is deliberately bounded to at most 256 deterministic signatures. It measures remove/reinsert and commit behavior without turning a large storage benchmark into a second full build. Candidate parity is checked before sync and again after reopen.

Persistent, lazy scalar, and lazy batch candidates are checked against the in-memory `LshIndex32` reference. A parity failure aborts the benchmark instead of emitting performance numbers for incorrect behavior.

## Compare two reports

```bash
cargo run --release -p pari-bench -- compare \
  baseline.json current.json \
  --output comparison.json
```

Only shared metrics with identical units and optimization direction are compared. Positive `improvement_percent` always means better, so lower latency or memory is normalized to the same sign convention as higher throughput or recall.

## Criterion microbenchmarks

Criterion is isolated from the main workspace so normal `cargo test --all-targets` does not execute timing benchmarks.

```bash
cargo bench --manifest-path benchmarks/criterion/Cargo.toml
```

The first microbenchmarks cover SHA-1 input hashing, one 128-permutation MinHash update, an in-memory LSH query, and 100,000 streamed union-find edges. End-to-end reports remain the primary evidence because a faster micro-kernel can be irrelevant if storage, allocation, or candidate volume dominates a real workload.

## Storage layout shootout

The isolated Criterion package also contains the storage-layout evaluation used before selecting Pari's local read path:

```bash
cargo run --release \
  --manifest-path benchmarks/criterion/Cargo.toml \
  --bin storage_layout \
  -- --items 5000 --queries 200 --output storage-layout-results.json
```

It builds the same deterministic bucket workload against three candidates:

1. `paged_file`: sorted bucket pages plus an offset directory and bounded reads;
2. `mmap_read_only`: the same page representation accessed through a read-only memory map;
3. `redb`: an embedded key-value store.

Each candidate must pass query-result parity before its timing data is accepted. The report records build throughput, reopen latency, file bytes, bytes/item, p50/p95/p99 query latency, batch throughput, and RSS after reopen where available.

Pari selected the explicit paged/segmented file design for the production local format. It keeps the runtime safe Rust path simple, avoids an embedded database dependency and runtime memory-map safety surface, and gives the storage layer direct control over compatibility checks, checksums, and bounded member reads. The shootout remains reproducible evidence rather than a hard-coded wall-clock CI gate.

## Real public set data: Kosarak

The FIMI Frequent Itemset Mining Dataset Repository publishes **Kosarak**, anonymized clickstream data from a Hungarian online news portal. The source repository is:

```text
https://fimi.uantwerpen.be/data/
```

After downloading and decompressing the Kosarak file, its whitespace-separated integer transactions can be consumed directly:

```bash
cargo run --release -p pari-bench -- run \
  --dataset /path/to/kosarak.dat \
  --items 10000 \
  --queries 100 \
  --overlap 20 \
  --output kosarak.json
```

The runner sorts and deduplicates each non-empty transaction. `--items` becomes the row limit. Queries retain up to `--overlap` source features and replace the remainder deterministically.

## Datasketch comparison

For overlapping MinHash and in-memory LSH semantics, an optional Python baseline emits the same JSON schema and metric names:

```bash
uv run --with 'datasketch>=2.0.0' \
  python benchmarks/datasketch_baseline.py \
  --items 5000 \
  --queries 100 \
  --output datasketch.json

cargo run --release -p pari-bench -- compare \
  datasketch.json pari-benchmark.json \
  --output pari-vs-datasketch.json
```

The baseline uses the same deterministic synthetic integer sets, query mutation, threshold, exact-Jaccard scoring, and 128-value affine32 MinHash configuration. Pari intentionally uses its own stable seed-to-permutation mapping, so signatures are not compared byte-for-byte; the comparison measures equivalent user-facing workloads instead.

## Scheduled benchmark workflow

`.github/workflows/benchmark.yml` runs `scale-100k` weekly and accepts `smoke`, `scale-100k`, or `scale-1m` on manual dispatch. It uploads:

- the validated campaign bundle and generated Markdown report
- `storage-layout-results.json`
- Criterion output

Scheduled results are review evidence, not a merge gate. Correctness, candidate parity, format validation, Rustfmt, Clippy, and tests remain the CI gates.

## Text deduplication and contamination workloads

The [text workload guide](text-workloads.md) provides streaming JSONL commands for corpus deduplication, reusable persistent reference indexes, and non-mutating cross-corpus audits. Each command emits a versioned machine-readable report with throughput, RSS where supported, index/output size, candidate reduction, and duplicate or overlap measurements suitable for the larger campaigns in issue #47.

## Datasketch migration benchmark

`benchmarks/datasketch_interop.py` measures an exact affine32 migration only after checking value-for-value signature parity and converted self-query recall. It reports Datasketch and Pari signature throughput, adapter import throughput, Pari build/query throughput, and index size. It intentionally does not compare LSH candidate sets because banding, bucket hashing, persistence, and execution models can differ. See the [compatibility matrix and migration guide](datasketch-v2.md).

## Named scale campaigns

List the committed profiles or inspect their exact commands without running them:

```bash
python scripts/benchmark_campaign.py profiles
python scripts/benchmark_campaign.py plan scale-100k
```

Run a profile from a clean worktree:

```bash
python scripts/benchmark_campaign.py run scale-100k \
  --output benchmark-artifacts/scale-100k \
  --include-text

python scripts/benchmark_campaign.py validate \
  benchmark-artifacts/scale-100k/bundle.json
```

The output directory must not already exist. A normal run refuses a dirty worktree because an artifact cannot honestly attribute uncommitted benchmark code to a Git SHA. `--allow-dirty` exists only for local smoke development; bundles produced that way are rejected as publishable evidence by default.

The `scale-10m` profile preserves failures because reaching a host limit is evidence for its architecture decision. If a stage fails or is interrupted, the requested output directory remains absent and the harness retains a sibling directory named `<output>.failed-<unique>/`. Its `failure.json` records the active stage, exact command, return code when a process started, failure phase and message, Git/worktree/profile provenance, host and filesystem telemetry, completed reports, and SHA-256 checksums for every available top-level report and log. If final publication fails after bundle validation, the staged bundle is marked failed and renamed `failed-bundle.json` before retention. If writing the bundle itself leaves malformed or partial bytes, those bytes are retained as checksummed `failed-bundle.partial`, which is not a JSON bundle and cannot validate or render.

Failure artifacts are diagnostic evidence, not successful or publishable benchmark bundles. The `validate` and `render` commands reject both failure manifests and failed bundle snapshots; only a transactionally published `bundle.json` has passed the campaign correctness gates. Before finalizing failure evidence, the harness verifies that its process-temporary directory was removed and that every retained top-level entry is a checksummed regular file. If cleanup fails or an unexpected directory remains, the harness leaves the hidden `.partial-*` staging directory for manual recovery, prints a warning, and does not write `failure.json` or claim a finalized failure artifact. Other profiles continue to clean failed staging directories by default. Pass `--preserve-failure-evidence` to opt into the same diagnostic retention while investigating another profile.

The automatic failure manifest records host identity plus total and free filesystem bytes. Mount/device type and cache state remain operator-recorded preflight telemetry for the canonical 10M run, as required below; the harness does not infer them from a portable Python API.

The profiles hold algorithm and workload semantics fixed while increasing scale:

| Profile | Synthetic items | Queries | Reference text items | Intended environment |
| --- | ---: | ---: | ---: | --- |
| `smoke` | 256 | 16 | 64 | normal CI and local correctness |
| `scale-100k` | 100,000 | 100 | 10,000 | weekly standard campaign |
| `scale-1m` | 1,000,000 | 100 | 100,000 | manual runner with at least 16 GiB RAM |
| `scale-10m` | 10,000,000 | 100 | 1,000,000 | dedicated Linux host with at least 128 GiB RAM and fast local scratch |
| `scale-100m-methodology` | 100,000,000 | 100 | 10,000,000 | planning only; see the preflight below |

Every synthetic query retains 29 of 32 source features and replaces three. Its exact Jaccard similarity to the source is therefore 29/35, just above the configured 0.8 threshold. This intentionally measures probabilistic recall near the LSH transition instead of using only identical self-queries.

The optional text stage generates a deterministic reference corpus and query corpus, plants exact cross-corpus matches, then runs the public `build-reference` and `audit --exact` workflow from `examples/text_workload.py`. Data generation is outside timed phases. Dataset sizes and SHA-256 digests are stored in the bundle.

Optional comparison stages are explicit:

```bash
python scripts/benchmark_campaign.py run smoke \
  --output benchmark-artifacts/comparison-smoke \
  --include-datasketch \
  --include-redis
```

Datasketch requires its optional Python dependency. Redis requires `PARI_REDIS_URL`. The Redis report records build and batch-query throughput, elapsed time, round trips by phase, round trips per item/query, and self-query recall.

## Bundle integrity and public reports

A bundle is accepted only when:

- report schema, configuration, and full Git SHA match the selected profile;
- required metrics are finite and use declared units and directions;
- scalar and batch candidates match;
- persistent and lazy candidates match the in-memory reference;
- persistence mutation parity still holds after reopen;
- exact ground truth contains at least one match;
- optional Redis self-recall and exact text-audit checks pass;
- every report checksum matches `bundle.json`.

Render one or more validated bundles into a public Markdown table:

```bash
python scripts/benchmark_campaign.py render \
  benchmarks/results/pari-scale-v1/SHA/scale-100k/bundle.json \
  benchmarks/results/pari-scale-v1/SHA/scale-1m/bundle.json \
  --output docs/benchmark-evidence.md
```

The weekly workflow uploads bundles under an artifact name containing both the profile and source SHA. Selected stable runs may be committed under `benchmarks/results/pari-scale-v1/<sha>/<profile>/`; later runs add evidence instead of rewriting previous measurements.

The current selected 100K and 1M results, bottleneck summary, and decision gates are published in [benchmark evidence](benchmark-evidence.md).

Signature thread-count and small-batch crossover measurements use `scripts/parallel_benchmark.py`. The implementation policy and profiler evidence are documented in [CPU parallelism](parallelism.md).

## Profiling CPU, allocations, and I/O

Build the profiled binary once, then collect profiles on a dedicated Linux host. Keep the generated profiler files beside the bundle and state whether caches were warm or cold.

```bash
cargo build --release -p pari-bench

# CPU samples and flamegraph for signature construction, index build, query,
# exact ground truth, mutation, and grouping in one annotated report run.
cargo flamegraph --package pari-bench --bin pari-bench \
  --output pari-bench.svg -- \
  run --items 100000 --queries 100 --set-size 32 --overlap 29 \
  --threshold 0.8 --num-perm 128 --seed 7 --output profile.json

# Allocation profile for the same deterministic workload.
heaptrack target/release/pari-bench \
  run --items 100000 --queries 100 --set-size 32 --overlap 29 \
  --threshold 0.8 --num-perm 128 --seed 7 --output allocation.json

# System-call and I/O mix for persistent build, reopen, and lazy query.
strace -c -f target/release/pari-bench \
  storage --items 100000 --queries 100 --set-size 32 --overlap 29 \
  --threshold 0.8 --num-perm 128 --seed 7 --output storage-profile.json
```

Use the phase elapsed metrics to keep harness-only exact-ground-truth cost separate from Pari runtime cost. In particular, do not cite ground-truth scanning as an index-query bottleneck. The profiler tools are external: see the [`flamegraph` project](https://github.com/flamegraph-rs/flamegraph) and [Heaptrack documentation](https://github.com/KDE/heaptrack).

## 10M and 100M preflight

Run `scale-1m` first and require a valid bundle. Before `scale-10m`, reserve at least 1.5 times the larger of measured peak RSS scaling and the host-level maximum RSS, plus 1.5 times the extrapolated persistent bytes/item on local scratch. Record mount type, available space, CPU model, memory, and cache policy.

The `scale-100m-methodology` profile cannot be executed by the campaign tool. A 100M run is approved only after a 10M bundle establishes all of the following:

1. peak memory and persistent bytes/item extrapolate within the dedicated host budget with 50% headroom;
2. candidate rate remains low enough that query aggregation and exact verification are bounded;
3. reopen and build I/O fit the allotted maintenance window;
4. CPU and allocation profiles identify product hot paths rather than benchmark ground-truth work;
5. the run can preserve the same correctness gates and full artifact provenance.

If those conditions fail, do not force a single-index 100M run and do not silently introduce sharding. Use the evidence to decide issue #69. Pari deliberately does not implement a distributed scheduler as part of this campaign.

## Capability comparison boundaries

This matrix describes public, source-verifiable capabilities. It is not a performance ranking.

| Capability | Pari | Datasketch 2.x | DataTrove | Fair comparison boundary |
| --- | --- | --- | --- | --- |
| Set/Jaccard MinHash threshold candidates | Native Rust/Python MinHash and LSH | `MinHashLSH` threshold candidates | Multi-stage MinHash deduplication pipeline | Match tokenization, hash width, permutations, bands/rows, threshold, and exact-verification policy before timing |
| Exact affine32 signature migration | Value-for-value adapter and golden fixtures | `affine32` is the 2.x default | No interoperability claim | Use `datasketch_interop.py`; do not infer identical LSH candidate sets |
| Persistent operation | Checksummed local `.pari`, lazy reopen, plus Redis backend | Redis and Cassandra storage are documented | Pipeline artifacts are written between distributed stages | Compare persistence only within the same operating model |
| Duplicate grouping | Direct candidate-pair and connected-group APIs | LSH returns unranked candidates for application verification | Dedicated bucket, cluster, and filter stages | End-to-end grouping is not a MinHash-kernel benchmark |
| Streaming text workload | JSONL deduplication, reusable reference build, and non-mutating audit | Library primitives rather than a fixed ingestion policy | Generator-based document pipelines and distributed executors | Use common input, normalization, shingling, retention, and output semantics |
| Broader algorithm families | MinHash/Jaccard is intentionally focused | Weighted MinHash, LSH Forest/Ensemble, HLL, and other indexes are documented | MinHash, sentence, and exact-substring dedup examples are documented | Algorithm availability is separate from persistence and throughput |

Primary sources: [Datasketch project and algorithm index](https://github.com/ekzhu/datasketch), [Datasketch LSH retrieval and storage semantics](https://ekzhu.com/datasketch/lsh.html), [DataTrove pipeline model](https://github.com/huggingface/datatrove), and [DataTrove's four-stage MinHash example](https://github.com/huggingface/datatrove/blob/main/examples/minhash_deduplication.py).
